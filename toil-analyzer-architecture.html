Toil Analyzer

1. Big picture

One GitLab repository is the product. Cloning it gives a team the analyzer, the shared signature catalog, their own properties file and the ledger of what they are killing. Nothing is hosted: the UI runs from the clone on a laptop, the schedule runs in GitLab CI (or Task Scheduler), and the multi-team view lives in Dynatrace.

Figure 1 — components and data flow. The engine is the same file in the browser, in the local server and in CI.

3. The engine, step by step

Everything below is pure JavaScript in lib/core.js. It runs identically in the browser, in server/report.js and in CI, and it never calls a model.

  1. Parse. parseCSV detects the delimiter (, ; tab |), honours quotes, doubled quotes and newlines inside quotes, strips a BOM.
  2. Map columns. detectMapping matches header names against patterns for twelve fields (number, short description, description, opened, resolved, assignment group, CI, category, priority, close notes, state, assigned). The Incidents view shows the mapping and lets you correct it; re-analysis is instant.
  3. Normalise. Dates are parsed leniently (2026-08-14 09:23:11, 08/14/2026 09:23 AM, 14/08/2026).
  4. Mask. maskText replaces volatile tokens so two incidents that differ only in a job name, host, ID or number collapse into one pattern. Team patterns run first (team.json → maskPatterns, e.g. \b(CTM|LN|PAY)_[A-Z0-9_]+\b → <job>), then the built-ins: 
    URLs → <url>   emails → <email>   INC/CHG/TASK/RITM/PRB numbers → <ticket>   GUIDs → <guid>   32-hex → <hash>
IPv4 → <ip>   ISO and US dates/times → <date> / <time>   yyyymmdd → <date>   paths → <path>
host-like tokens (app-node-07, ora-p1.corp.local) → <host>   percentages → <pct>   remaining numbers → #
"Control-M job CTM_LN_ACQ_FEED_D ended NOT OK (RC=12)"  →  "control-m job <job> ended not ok rc=#"
  5. Signature. The catalog is tried first: each signature's regex (case-insensitive) against the fields it names (default short description + description), highest priority first, first match wins. Matched incidents get the catalog id and name (known). Everything else gets an automatic id: the first eight non-stopword tokens of the masked text, hashed (auto-xxxxxxxx) — that is an unknown pattern, the raw material for a signature proposal.
  6. Cluster. Incidents group by signature id. Per cluster: count, per-month rate, first/last seen, weekly counts across the window, groups and CIs, inter-arrival gaps, automatable-keyword hits, masked close-note histogram, five evenly spaced samples, component (from team.json → components[].match, then tags).
  7. Score, hours, savings — section 4.
  8. Rank. Offenders sort by score × ln(count + 1): volume matters, but a noisy singleton never outranks a weekly repeat.

4. Scoring, hours and savings

Toil score (0–100)

score = 100 × (0.35·repetition + 0.30·automatable
             + 0.15·regularity + 0.20·uniformity)

repetition  = log10(count) / log10(50), capped at 1
automatable = share of incidents whose text/notes contain
              an automatable keyword (restart, rerun, unlock,
              expired, cert, disk, requeue, …; team can override)
regularity  = 1 − CV(inter-arrival gaps)/2, clamped 0..1
              (needs ≥ 3 gaps; periodic causes score high)
uniformity  = share of the most common masked close note
              (0.5 when there are no notes)

Flags: toil = score ≥ threshold (60) and count ≥ 2; repetitive = count ≥ 5; automatable = automatable ≥ 0.5; unknown = no catalog match. Threshold and minimum live in team.json → toil.

Hours and money

technical h / incident  (ops effort)
  = signature.hours.technical
    ?? hoursModel.byCategory[category]
    ?? hoursModel.technicalPerIncident        (default 0.75)

business h / incident   (waiting, manual workaround)
  = min(resolved − opened, elapsedCapHours)  (default cap 8)
    ?? signature.hours.business
    ?? hoursModel.businessPerIncident         (default 1.5)

USD = hours × rates.technical (85) | rates.business (60)
perMonth = count / months in window  (months = days / 30.44, ≥ 1)

The split is deliberate: technical hours are what automation removes from the on-call plate; business hours are what the business stops waiting for. Both appear separately everywhere.

Savings

factor by disposition:  eliminate 1.0   selfheal 0.9   automate 0.8   tune 0.5   accept / review 0
hours saved per month   = (technical + business per incident) × perMonth × factor
USD saved per year      = 12 × perMonth × factor × (tech/inc × rate.technical + biz/inc × rate.business)

Projected  = every toil candidate at its disposition factor            (what is on the table)
Committed  = offenders in Ticketed, Fixed or Verified                    (what someone owns)
Verified   = (baseline perMonth − post-fix perMonth) × hours/incident    (what the data proves)

The default disposition comes from the catalog entry, otherwise automate for toil candidates and review for the rest; the drawer, or a Claude verdict, changes it per offender.

5. The kill chain ledger

ledger/<team>/ledger.json holds one entry per tracked pattern: state, history, disposition, Jira key, owner, the baseline captured when the pattern was first registered (per-month rate and hours per incident — kept even after the incidents disappear, which is the point), the latest observation, verification windows and the AI cost spent on it. Toil candidates register automatically as Detected on every analysis.

Figure 2 — states and who moves them. Only Detected → Ticketed needs a human every time; the rest can come from Jira and the data.

Verification logic (advanceLedger)

  • For a Fixed pattern the fix time is the anchor. The window since then is cut into 7-day slices; after two full slices with zero matching incidents the pattern becomes Verified automatically.
  • For a Verified pattern any matching incident after the fix time flips it to Regressed with the count in the note.
  • The post-fix rate (incidents since the fix ÷ months since the fix) is stored on latest.postFix and is what verified savings are measured against — the 90-day window would otherwise dilute a fix made three weeks ago.
  • Both the UI (after every load) and server/report.js (on schedule) run this; the schedule is what makes it happen without anyone opening the tool.

6. The Claude step

Claude Code is used for the one thing the deterministic engine cannot do well: decide what a pattern means and draft the fix. It is invoked per offender, on click, with a small packet, and the answer is a typed JSON verdict the UI can apply.

7. Scheduled progress

Two scripts, deterministic, safe for a scheduler. GitLab CI runs them from .gitlab-ci.yml on a schedule; the same two lines work from Windows Task Scheduler or cron on the SRE box if runners cannot reach ServiceNow or Dynatrace.

node server/pull.js   --team example-team [--days 90]   # ServiceNow Table API → data/<team>-<yyyymmdd>.csv
node server/report.js --team example-team --push        # analyze → Jira sync → advance ledger → summary → report → Dynatrace
# --all runs every team; --file x.csv analyses a file instead of the latest pull; --no-jira skips the Jira step
  1. pull.js builds sysparm_query from team.json → servicenow: opened_at ≥ now − days ^ assignment_group.nameIN… ^ cmdb_ci.nameIN… ^ extraQuery, fetches the listed fields as display values, pages by 1000 and writes the CSV the UI reads.
  2. report.js re-runs the engine on the newest file, auto-registers new toil candidates, asks Jira about every Ticketed/Fixed offender with a key (Done → Fixed; reopened → Ticketed), advances Fixed → Verified / Verified → Regressed, writes ledger/<team>/summary.json (what the executive rollup reads) and reports/<team>/YYYY-Www.md, then pushes metric lines and one business event per transition.
  3. With CI_PUSH_TOKEN the job commits ledger/ and reports/ back to the default branch with ci.skip. The UI's Sync repo is stash-aware, so a laptop with uncommitted ledger moves still fast-forwards; a genuine conflict is reported and left for git.

11. Security and data handling

  • Where data lives. Raw dumps: data/, git-ignored. Verdict cache: analysis-cache/, git-ignored. Ledger and summaries: committed, containing pattern names, counts, states, Jira keys and verdicts — not incident records. Unknown patterns are named by masked text, so mask anything sensitive with maskPatterns before it can appear there.
  • What leaves the machine. To Claude Code: the packet (five raw sample short descriptions and close-note excerpts, counts, team context) through your enterprise Claude Code login — no API key is stored anywhere. To Dynatrace: numbers and dimension names. To Jira: issue keys. To GitLab: the proposal file.
  • Server. Binds 127.0.0.1, no listener on the network, cross-origin state changes refused, paths sanitised (basename, id regex).
  • Secrets. .env is git-ignored; CI uses masked variables with the same names. Prefer an ActiveGate URL and a ServiceNow service account scoped to read incidents. Corporate CA via NODE_EXTRA_CA_CERTS.
  • Regexes are code. A pathological signature regex runs against every incident in every team's browser; reviewers should reject nested quantifiers ((a+)+) and CI's sample test makes overlap visible.

12. Running it: setup, rhythm, troubleshooting

Setup once

  1. Push the repo to GitLab; replace the CODEOWNERS handles; paste real brand hex values at the top of ui/index.html.
  2. Create teams/<id>/team.json from the example (Settings → New team from this does it in the UI) and open the MR.
  3. On the SRE box: git clone, .env from .env.example, npm start. npm test confirms the engine, schemas and signatures.
  4. Add a CI schedule (weekly is enough) with the masked variables; or a Task Scheduler job running the two scripts.
  5. Dynatrace: one dashboard, tiles per metric above, filter by team. Business events view for milestones.

Weekly rhythm

  1. Schedule pulls and reports; the ledger moves Fixed → Verified on its own; Jira moves Ticketed → Fixed.
  2. An SRE opens the tool, works the top offenders: analyze, set disposition, create the Jira from the copied text, mark Ticketed; propose signatures for the biggest unknowns.
  3. Commit & push ledger. The executive view (or Present mode) reads straight from it; the report goes to Confluence if wanted.

13. Known limits and next steps

  • Business hours are elapsed time capped per incident, not calendar-aware working hours. A business-calendar option in hoursModel is the obvious refinement.
  • ServiceNow OAuth tokens are used as given; there is no refresh flow. Long-lived service-account basic auth or a token helper in CI covers the schedule.
  • The Jira sync moves states only; it does not create issues. Copy Jira text plus a Jira MCP in Claude Code is the interactive path; a create endpoint would be ~30 lines in lib/jira.js.
  • Claude Code's own OpenTelemetry export can add interactive-session usage to Dynatrace; the tool's toil.ai.cost_usd already covers every run it starts.
  • A ServiceNow MCP wrapper over lib/servicenow.js and a Confluence publish step for the weekly report are the two most requested add-ons; both are Node-only and contained.
